# Contributing

First off, thanks for taking the time to contribute! We're excited to see what you've got.

This project is all about reducing user friction. Every change should make the tool easier or more intuitive to use. If you're ever unsure, ask yourself: "Does this make the user's life better?"

## How Can I Contribute?

### Reporting Bugs

- **Check if the bug already exists** in the project's issue tracker.
- If it doesn't, create a new issue. Be sure to include a clear title and a detailed description.
- Describe the exact steps to reproduce the bug.
- Explain what you expected to happen and what actually happened.
- Include details about your environment (OS, tool version, etc.). This helps us track it down faster.

### Suggesting Enhancements

- We love new ideas! Before you start coding, please open an issue to discuss the feature.
- Explain the problem you're trying to solve. Why is this feature needed? What user friction does it remove?
- We'll discuss the idea and figure out the best way to implement it. This saves everyone time and makes sure your hard work gets merged.

### Pull Requests

Ready to write some code? Great!

1.  **Fork the repo** and create your branch from `main`.
2.  **Set up your local environment.** You should be able to get started with `npm install` (or the equivalent for this project).
3.  **Make your changes.** Keep them focused. One PR should solve one problem.
4.  **Add tests.** If you're adding a new feature, it needs tests. If you're fixing a bug, add a test that catches the bug.
5.  **Ensure the test suite passes.**
6.  **Format your code.** We use an automated formatter to keep things consistent. Run it before you commit.
7.  **Commit your changes.** Use a clear and descriptive commit message.
8.  **Push to your fork** and submit a pull request to the `main` branch.
9.  **In your PR description,** explain the "why" behind your change and link to any relevant issues.

## Coding Style

We value clarity and readability above all else.

-   **Readable code over clever code.** If you have to write a comment to explain what a line of code does, it's probably too complex.
-   **Short functions with clear names.** A function should do one thing and do it well. Its name should describe what it does.
-   **Product-minded.** Always think about the end-user. Good error messages are a feature. A smooth onboarding experience is critical.

We enforce these standards with a linter. Please make sure your code is clean before submitting.

Thanks again for your contribution
